# Electron Mac 重构方案自审记录

日期：2026 年 10 月 14 日。范围：[Spec](2026-10-14-electron-mac-spec.md)、[Plan](2026-10-14-electron-mac-plan.md) 与现有业务实现。此次只修订文档，未安装 Electron、迁移数据或停止正式服务。

> 同日进行了第二轮评审，部分结论已被取代，详见文末“第二轮评审与修订”。第一轮记录保留，用于追溯。

## 审查结论

“Electron 界面 + 独立采集后台 + Mac 适配层”的方向可以继续，但原计划存在六组需要先补齐的设计缺口。已直接修订 Spec 和 Plan；建议先实施任务 1 的实际打包验证，通过后再迁移业务。

以下“已修订”表示设计和施工要求已补齐，不表示代码已实现或真机验收已通过。

## 发现与修订

### 1 重要：首次设置和后台停止后缺少业务入口

原计划把所有设置和导出命令放在 agent 的 worker，但引导要求先填写资料、之后才启用 agent。首次启动会遇到先后顺序矛盾，停止后台后也无法核对、导出。

修订：agent 增加仅业务模式，由用户打开界面时按需启动，无采集、菜单栏或登录注册，界面退出后结束。启用采集时关闭原 worker，再交给登录后台；两个模式共用同一实例约束。任务 1、4、6、9 增加未授权、被系统禁用、交接中断和单一工作进程验证。

这增加了一个模式及其交接流程，但避免为了导出而强迫同事开启采集。该模式在后台权限关闭后的真实行为必须由任务 1 验证，不能只依据接口文档认定可行。

### 2 重要：内存事件队列不能覆盖进程崩溃

原计划只把 worker 重启期间的事件放入 4096 条内存队列。agent 自身崩溃会丢掉队列；系统历史也不能还原当时的网络探测结果。

修订：电源／网络事实先写本机可恢复日志，再送 worker；数据库提交后确认，崩溃后幂等重放。增加日志损坏、半条写入、磁盘满、容量上限和孤儿子进程测试。迁移期间保留指定日志范围，避免刚清理的事实又被回退流程需要。任务 4、5、11、12 负责。

保证范围是已成功持久化的事实；睡眠或突然断电前尚未完成写入的最后事件仍须实测并提示人工核对。

### 3 重要：快照版本没有覆盖资料和模板

检查现有 `src/lib/day-draft.ts` 后确认，`monthRevision()` 只包含日期、类别、上下班时间和备注。直接复用它，修改姓名、交通费、模板或午休规则后，旧邮件／文件可能仍被认为有效。

修订：桌面版新增完整快照版本，覆盖记录、确认／锁定、个人资料、模板内容和业务规则。复制／导出在可信工作进程中重新比较，变化时要求刷新。导出保存生成输入版本和提交后版本，避免导出时锁定月份导致自己刚生成的文件立即失效。任务 3、7、8、12 增加对应验证；原 Web 的版本函数保持兼容。

### 4 重要：失败回退可能覆盖切换期间的新数据

原计划有在线备份和停止旧服务后的冻结备份，但新 agent 开始写入后再恢复冻结备份，仍可能丢失切换期间的新事实。

修订：切换完成前禁止人工修改和正式导出；回退优先保留兼容的当前库。必须恢复备份时，先另存当前库，再重放切换期间保留的事实，不能仅恢复旧备份就报告成功。无法完整恢复时保留材料并明确报错。自动回退限定在迁移未完成期间；完成后降级另行核验 schema 兼容。任务 11、12 负责。

### 5 重要：人工升级缺少进程结束后的执行主体

原计划写了停止、替换和恢复，但未明确旧进程都退出后由谁接着执行，也未规定升级中断后的入口。

修订：旧应用的“准备升级”负责备份、记录状态、停止并取消注册，用户在 Finder 替换应用；新应用启动前读取恢复记录，再恢复原启用选择。旧应用重新打开也能取消未完成升级。保留旧包副本、最终冻结备份和 schema 兼容信息，避免在线备份遗漏最后新增事实。任务 10、12 负责。

### 6 一般：部分施工前置条件和过渡期约束不完整

原任务 9 使用任务 11 才创建的旧安装识别；任务 6 提前使用桌面测试入口；公共组件改为桌面调用后，保留的 Web 可能无法继续构建；后续增加回执表还会与硬编码的迁移版本 2 冲突。

修订：只读识别移到任务 2；任务 1 创建最小窗口、测试配置和脚本；任务 7 使用共享组件加两端操作适配，并依赖任务 6；迁移版本按执行时下一版本追加。另补持久化操作回执，超时后先查执行结果，未确定前仍禁止提交，避免仅重新读取就过早解除阻塞。各任务增加对应文件和验证命令。

## 第二轮评审与修订

日期：2026 年 10 月 14 日。依据：对照现有代码复核两份文档，并确认了两项项目前提：一是旧版只部署在维护者一台电脑上；二是没有 Apple 开发者账号，程序员同事从仓库自行构建，非程序员同事由维护者直接发送应用包。

### 前提变化带来的修订

- **分发方式：** 取消 Developer ID 签名、公证和 DMG。程序员执行 `npm ci && npm run desktop:install`，在本机构建、临时签名（可选本机自建证书）并安装；非程序员使用维护者打出的通用包，按图文说明首次打开。
- **升级：** 取消应用内的“准备升级”流程和升级 journal。程序员升级由安装脚本在应用外部完成，脚本负责停止后台、替换应用、恢复后台；非程序员升级是先停止后台，再替换应用，然后重新启用。
- **旧版迁移：** 只涉及维护者一台电脑，改为一次性脚本。旧程序在库版本较新时会直接跳过迁移（`src/lib/db/index.ts:40`），只要新迁移只追加表或可空列，回退时放回旧启动项即可，不需要双备份和事实重放。

### 架构简化

- **取消“只允许一个数据库工作进程”的约束。** 现有的采集程序和 Web 服务已经在用 WAL、等锁时间、迁移写锁和维护租约共享同一个库。这条约束取消后，以下内容随之删除：
  - agent 的仅业务模式及模式交接；
  - 自建事件日志与事实回执；
  - 本机 socket、认证 token 和协议握手。
- **新结构：**
  - **gui：** 自带业务工作进程。
  - **agent：** 自带采集工作进程，事件直接写库，采集连接使用完全同步写入。
  - **角色之间：** 不建立常驻通信。状态通过数据库记录和 `launchctl` 查询；启停通过写入或移除启动项完成。
- **取消操作回执。** 现有的保存、恢复、批量确认、锁定对重复的相同请求不会产生新的修改；工作进程又按顺序执行请求。所以工作进程崩溃或超时后，重新读取快照就能得出确定的状态。“重新读取成功前禁止复制和导出”这条规则保留。
- **后台注册改用 launchd。** 启动项写入 `~/Library/LaunchAgents` 并用 `launchctl` 加载，这是仓库中已经验证过的方式；不再使用 SMAppService 和 Swift 桥接程序。好处有三点：不依赖签名身份，安装脚本可以直接启停后台，“已启用”的唯一依据就是启动项文件是否存在。
- **取消导出产物表。** 沿用现有“先写文件、后登记导出／锁定”的顺序，最近一次导出的位置由 gui main 在内存中保存。首版因此不需要新增数据库迁移。

### 新发现的问题及处理

| 问题 | 处理 |
| --- | --- |
| 同一应用包的 agent 运行时，从 Finder、程序坞打开应用的请求可能被系统交给 agent | 任务 1 实测各种打开方式；用 `LSUIElement` 加 gui 主动显示程序坞图标，agent 收到打开请求时转为启动 gui；不成立时改用独立辅助应用包 |
| 由 launchd 启动的后台写入用户选的导出目录，会触发隐私授权或被拒绝 | 工作进程只写数据目录，复制和另存由 gui main 完成 |
| 仅业务模式不跑维护，从未启用后台的使用者没有自动备份 | 两种角色都按租约执行维护 |
| 读取月表会写 `day_auto` 并可能清除确认，并不是纯读取 | 写入规格说明；revision 在无人工操作时也可能变化，界面需提示原因 |
| 开发用 Node 22，Electron 内置 Node 24 | 开发和 CI 改用 Node 24（不低于 24.15.0） |
| 打包配置未提及 Electron fuses | 任务 9 关闭 RunAsNode 等开关，开启 ASAR 完整性校验 |
| 临时签名的身份每次构建都会变化 | 任务 1 实测影响；安装脚本支持本机自建证书 |
| 带隔离标记的应用在随机转移位置运行，会让启动项指向失效路径 | 检测运行位置，提示先移动到应用目录再启用 |
| 旧程序目录位于数据目录的 `app/` 下，其中含 `.env.local` | 新缓存不使用 `app/`；迁移不删除该目录，验收后由维护者手动清理 |

### 第一轮结论的现状

| 第一轮条目 | 现状 |
